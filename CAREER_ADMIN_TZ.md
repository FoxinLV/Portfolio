# Техническое задание: локальный редактор карьеры

## 1. Общая информация

**Название:** Portfolio Admin — Career  
**Тип:** локальное однопользовательское web-приложение  
**Назначение:** создание, проверка, предпросмотр и публикация карьерных данных в Yandex Object Storage  
**Публичный потребитель:** React + Vite портфолио на GitHub Pages  
**Основной объект:** `portfolio/career/career.json`  
**Контракт:** [CAREER_DATA_CONTRACT.md](./CAREER_DATA_CONTRACT.md)

Редактор является расширением существующей концепции Portfolio Admin из `ADMIN_TZ.md`, а не отдельной конкурирующей CMS.

---

## 2. Цель

Локальный редактор должен позволять владельцу без ручного редактирования JSON:

- добавлять компании, заказчиков и собственные проекты;
- создавать несколько ролей в одной организации;
- связывать должности явным переходом: повышение, смена направления, расширение ответственности или возвращение;
- раздельно описывать обязанности, фактическую работу, достижения и ключевые факты каждой должности;
- указывать параллельные периоды работы;
- видеть пересечения на временной шкале до публикации;
- связывать опубликованные и черновые проекты портфолио с конкретной ролью;
- описывать вклад в проект именно в контексте этой работы;
- загружать логотипы и обложки организаций;
- проверять все ссылки и даты;
- публиковать согласованный `career.json` и медиа в S3;
- безопасно восстанавливать предыдущую версию.
- генерировать или загружать PDF-резюме и публиковать управляемую ссылку на hh.ru.

---

## 3. Границы системы

### Входит в первую версию

- CRUD организаций;
- CRUD ролей/периодов занятости;
- редактор переходов между должностями;
- CRUD назначений проектов;
- отображение параллельных периодов;
- drag-and-drop порядка внутри одинаковых дат;
- предпросмотр desktop/mobile;
- runtime-валидация JSON Schema;
- кросс-валидация с проектами из S3;
- загрузка и оптимизация логотипов/обложек;
- draft/published/archived;
- импорт/экспорт JSON;
- diff перед сохранением;
- ETag-защита от внешнего изменения;
- локальные резервные копии;
- журнал операций;
- публикация в Yandex Object Storage.
- генерация/загрузка PDF-резюме и настройка ссылки hh.ru.

### Не входит

- публичная авторизация;
- многопользовательское редактирование;
- база данных;
- HR-система, зарплата, табель и документы;
- автоматическое чтение резюме из HeadHunter/LinkedIn;
- хранение трудовых договоров и персональных документов;
- автоматическая генерация достижений через внешний AI;
- изменение исходного кода GitHub Pages при каждой публикации.

## 4. Архитектура

```text
Browser: Portfolio Admin
          │ localhost
          ▼
Local Admin API (127.0.0.1)
          │
          ├── JSON Schema / cross validation
          ├── image processing
          ├── local backups and audit log
          └── signed S3 requests
                    │
                    ▼
           Yandex Object Storage
                    │ public GET
                    ▼
             GitHub Pages portfolio
```

Секреты S3 находятся только в локальном API. Browser-клиент Local Admin не получает секретный ключ и не выполняет подписанные S3-запросы самостоятельно.

## 7. Временная шкала редактора

Это основной рабочий экран для проверки параллельной занятости.

### Представление

- горизонтальная шкала лет и месяцев;
- отдельная дорожка для каждого одновременного интервала;
- цвет роли берётся из `accentColor` организации/роли;
- открытый период продолжается до вертикальной линии «Сегодня»;
- назначения проектов отображаются вложенными сегментами внутри роли;
- переход между должностями отображается узлом/стрелкой с датой и типом;
- масштаб: год, квартал, весь период;
- возможность скрыть archived и draft;
- tooltip/панель по клику с названием, датами и проектами.
- общий период в компании показывается отдельно от длительности каждой роли.

### Алгоритм дорожек

Интервалы сортируются по началу и распределяются по минимальному числу дорожек так, чтобы пересекающиеся интервалы не накладывались. Это визуальное размещение и не создаёт приоритета между работами.

### Предупреждения

- роль без организации;
- роль без описания;
- пересечение ролей одной компании;
- три и более текущих ролей;
- назначение проекта выходит за даты роли;
- проект связан с несколькими ролями в один период;
- переход создаёт цикл или ведёт к роли другой компании;
- очень короткий период, который невозможно прочитать на текущем масштабе.

Пересечение работ само по себе не является ошибкой.

## 8. Редактор организации

### Поля

- ID;
- статус;
- полное название;
- короткое название;
- тип организации;
- отрасль;
- год основания;
- описание;
- сайт;
- местоположение;
- логотип;
- cover;
- порядок;
- структурированные факты о компании;
- вычисляемый общий срок работы в компании;
- количество отдельных периодов работы;
- список связанных ролей;
- список связанных проектов, вычисляемый через роли.

### Работа с изображениями

- drag-and-drop и кнопка выбора файла;
- входные форматы: PNG, JPEG, WebP, SVG;
- проверка сигнатуры и MIME type;
- raster logo: WebP до 512×512;
- cover: WebP, рекомендуемое соотношение 16:6, максимум 1920 px;
- прозрачность логотипа сохраняется;
- SVG очищается от scripts, внешних ссылок и событий;
- предпросмотр на светлом и тёмном фоне;
- загрузка в prefix конкретной организации.

Удаление организации запрещено, пока существуют роли. Сначала роли архивируются/переносятся либо удаляются с явным подтверждением.

Карточка редактора организации должна показывать вычисляемое резюме:

```text
В компании: 3 года 7 месяцев
Периодов работы: 2
Должностей: 3
Проектов: 6
```

Продолжительность считается по объединению интервалов ролей этой компании. Пересекающиеся должности не суммируются дважды, а перерыв между увольнением и возвращением не включается.

## 9. Редактор роли

### Поля

- ID;
- статус;
- организация;
- должность/роль;
- тип занятости;
- режим работы;
- дата начала;
- дата окончания либо «по настоящее время»;
- точность отображения даты;
- местоположение;
- краткое описание;
- обязанности;
- фактическая деятельность — «Что делал»;
- достижения;
- ключевые факты роли;
- переход с предыдущей должности;
- технологии;
- навыки;
- цвет;
- «выделить на странице»;
- порядок;
- связанные проекты.

### UX дат

- checkbox «Работаю сейчас» очищает `endDate`;
- ввод месяца по умолчанию, точность «месяц»;
- при точности «год» сохраняется техническая дата `YYYY-01-01`, но UI показывает только год;
- продолжительность пересчитывается сразу;
- рядом показываются другие роли, пересекающиеся с выбранным периодом;
- система не предлагает автоматически завершить предыдущую работу.

### Списки обязанностей и достижений

- добавление клавишей Enter;
- изменение порядка;
- удаление с undo;
- ограничение: 300 символов на пункт;
- дубликаты подсвечиваются;
- достижения рекомендуется формулировать как результат, но это подсказка, не блокирующая проверка.

### Семантика блоков должности

- «О должности» — краткий смысл роли;
- «Обязанности» — зона ответственности;
- «Что делал» — конкретные регулярные действия и виды работ;
- «Результаты» — достигнутые изменения и измеримые эффекты;
- «Ключевые факты» — короткие пары `название → значение`, выводимые в конце карточки.

Редактор не объединяет эти поля автоматически, потому что они отвечают на разные вопросы.

### Редактор перехода между должностями

Для новой роли можно включить «Это переход с другой должности» и заполнить:

- предыдущую роль;
- тип перехода;
- дату;
- публичный заголовок;
- пояснение;
- показывать ли переход акцентно.

Типы:

```text
Повышение
Горизонтальный переход
Расширение ответственности
Изменение формата сотрудничества
Возвращение в компанию
Реорганизация
Другое
```

После выбора предыдущей роли новая роль наследует организацию. Дата перехода по умолчанию равна дате начала новой роли. UI показывает связку:

```text
Разработчик
Январь 2022 — Январь 2024
        ↓ Повышение · Февраль 2024
Старший разработчик
Февраль 2024 — настоящее время
```

Циклы, ссылка роли на саму себя и переход к несуществующей роли блокируются. Пересечение исходной и новой должности допускается как период передачи обязанностей, но требует просмотра предупреждения.

## 10. Связывание проектов с карьерой

### Выбор проекта

Редактор загружает все `portfolio/projects/*/project.json`, включая draft и archived для административного выбора. В selector показываются:

- обложка;
- название;
- ID;
- статус;
- дата проекта;
- уже существующие карьерные связи.

### Поля назначения

- роль/период занятости;
- проект;
- даты участия;
- роль именно в проекте;
- описание вклада;
- типы участия;
- ключевые результаты;
- featured;
- порядок;
- статус связи.

### Быстрое связывание

Поддержать оба сценария:

```text
Роль → Добавить проект
Проект → Добавить карьерный контекст
```

Оба сценария редактируют один объект `ProjectAssignment` в `career.json`.

### Массовые операции

- привязать несколько проектов к одной роли;
- перенести выбранные связи на другую роль;
- архивировать связи вместе с ролью;
- изменить статус нескольких связей;
- проверить отсутствующие проекты.

### Защита целостности

Физическое удаление проекта из Object Storage при существующей связи должно быть заблокировано существующим Portfolio Admin либо требовать предварительного удаления/архивации назначения.

## 11. Предпросмотр

Предпросмотр использует те же React-компоненты и правила фильтрации, что публичный сайт, насколько это возможно.

Режимы:

- desktop 1440 px;
- tablet 768 px;
- mobile 375 px;
- timeline;
- организации;
- выбранная карьерная запись;
- выбранная страница проекта с карьерным контекстом.

Предпросмотр должен уметь показывать:

- только опубликованные сущности;
- все сущности с административными статусами;
- состояние без логотипов;
- три параллельные работы;
- длинные названия;
- роль без проектов;
- проект с несколькими карьерными контекстами.
- несколько должностей одной компании с переходами;
- карточку компании с рассчитанной общей продолжительностью;
- кнопки PDF и hh.ru.

## 12. Раздел «Резюме»

### Назначение

Раздел управляет двумя независимыми публичными действиями:

1. «Скачать PDF-резюме» — файл находится в Yandex Object Storage.
2. «Резюме на hh.ru» — внешняя HTTPS-ссылка, добавляемая владельцем.

### PDF

Поддержать два сценария:

- генерация PDF из опубликованных карьерных данных;
- загрузка готового PDF вручную.

Для генерации рекомендуется HTML/CSS-шаблон и headless Chromium/Playwright на локальном сервере. Требования:

- формат A4;
- выделяемый текст, а не изображение страниц;
- встроенные или системно безопасные шрифты;
- кликабельные HTTPS-ссылки;
- номер страницы при двух и более страницах;
- дата обновления;
- не включать draft/archived;
- отдельный предпросмотр до загрузки;
- базовый шаблон «Краткое резюме» на 1–2 страницы;
- расширенный шаблон может быть добавлен позднее;
- имя файла безопасно и задаётся в настройках;
- итоговый файл проверяется открытием и размером.

Настройки PDF:

- включить публичную кнопку;
- заголовок и профессиональная специализация;
- краткое описание;
- контакты, разрешённые для публикации;
- выбирать роли и проекты;
- показывать/скрывать логотипы компаний;
- язык;
- шаблон;
- имя скачиваемого файла.

При ручной загрузке: только валидный PDF, ограничение размера, проверка сигнатуры `%PDF`, запрет активного содержимого по возможности, безопасное имя и preview.

### hh.ru

Поля:

- включить кнопку;
- URL резюме;
- подпись кнопки;
- дата ручной проверки ссылки;
- необязательная заметка только для администратора.

Разрешать только `https://hh.ru/...` и документированные поддомены hh.ru. Local Admin выполняет безопасную проверку формата URL, но не должен входить в аккаунт hh.ru, хранить cookies или парсить приватное резюме.

Если hh.ru требует авторизацию или не разрешает прямое скачивание, публичная кнопка называется «Резюме на hh.ru», а не обещает скачивание файла.

### Публикация

PDF загружается до `career.json`. Поле `resume.pdf.path` записывается только после успешной проверки объекта. Замена PDF создаёт локальную резервную копию метаданных; предыдущий файл можно хранить под версионированным ключом до успешной публикации.

## 14. Сохранение и публикация

### Локальный черновик

- изменения формы автоматически сохраняются локально каждые 5 секунд;
- автосохранение не пишет в S3;
- после аварийного закрытия предлагается восстановление;
- локальный draft привязан к исходному ETag.

### Сохранение draft в S3

Допускается сохранить корневой `career.json` со статусом `draft`. Публичный сайт игнорирует его и показывает последний локально закэшированный опубликованный снимок только если такая стратегия явно реализована. Предпочтительнее хранить публичный `career.json` только опубликованным, а удалённые черновики — под закрытым административным prefix.

Рекомендуемая схема:

```text
portfolio/career/career.json          # только публичная версия
portfolio-admin/drafts/career.json    # непубличный draft
```

### Порядок публикации

1. Повторно прочитать `career.json` и проверить ETag.
2. Загрузить новые изображения во временные ключи.
3. Проверить их чтение и метаданные.
4. Скопировать/переименовать в итоговые ключи.
5. Загрузить связанные неизменённые объекты при необходимости.
6. Сформировать финальный JSON.
7. Выполнить JSON Schema и cross-reference validation.
8. Создать локальную резервную копию предыдущего JSON.
9. Записать новый `career.json` последним.
10. Повторно прочитать его и сравнить checksum.
11. Очистить временные объекты.

Если шаг до записи `career.json` завершился ошибкой, публичная версия не меняется.

---

## 15. Конфликты и ETag

При открытии сохраняется ETag версии из S3. Перед публикацией выполняется условная запись.

Если ETag изменился:

- публикация блокируется;
- показывается diff «S3 / локальная версия»;
- доступны действия «обновить из S3», «экспортировать локальную версию», «объединить вручную»;
- принудительная перезапись доступна только после отдельного подтверждения и создания backup.

## 16. Резервные копии

Перед каждой перезаписью:

```text
.portfolio-admin/backups/
└── career/
    └── 2026-10-07T15-00-00Z/
        ├── career.json
        └── metadata.json
```

`metadata.json` содержит:

- исходный ETag;
- checksum;
- время;
- причину операции;
- версию Local Admin;

## 19. Валидация

Три уровня:

1. поле формы — немедленная понятная ошибка;
2. полный документ — JSON Schema;
3. внешние связи — фактические `project.json` и S3-объекты.

Перед публикацией обязательно проверить:

- уникальность ID;
- даты и диапазоны;
- родительские ссылки;
- существование проектов;
- совместимость статусов;
- существование медиа;
- HTTPS URL;
- безопасные относительные пути;
- отсутствие опасного HTML;
- поддерживаемую schemaVersion;
- доступность итогового публичного URL.
- целостность переходов между должностями;
- существование включённого PDF;
- допустимый домен hh.ru;

Ошибки блокируют публикацию, предупреждения требуют просмотра, но могут быть приняты.

## 22. Безопасность

- Local Admin API слушает `127.0.0.1`;
- проверяет `Host` и `Origin`;
- S3 credentials только в server environment;
- credentials не попадают в frontend bundle, localStorage и логи;
- ограниченные CORS и security headers;
- лимиты тела запроса и файлов;
- защита от path traversal;
- allowlist расширений, MIME и сигнатур;
- sanitize SVG;
- запрет исполнения загруженных файлов;
- операции удаления ограничены prefix `portfolio/career/`;
- физическое удаление требует подтверждения ID;
- публичный JSON проверяется на потенциальные секреты и приватные данные.
- PDF не должен содержать draft-записи, локальные пути и административные заметки;
- URL hh.ru нормализуется и не допускает `javascript:`, редиректы через пользовательские схемы и подмену домена.

## 23. Приватность

Форма публикации показывает предупреждение:

```text
Карьерные данные будут доступны публично.
Не публикуйте зарплату, договоры, личные контакты коллег,
внутренние адреса, закрытые названия систем и конфиденциальные результаты.
```

Не предусматривать поля для:

- зарплаты;
- ФИО руководителей;
- личных телефонов и email коллег;
- юридических документов;
- внутренних IP/доменов;
- причин увольнения;
- оценки работодателя.

## 27. Критерии готовности

1. Раздел «Карьера» доступен в Portfolio Admin.
2. Можно создать организацию и несколько ролей.
3. Можно сохранить три одновременно активные работы.
4. Timeline наглядно показывает пересечения.
5. Пересечение разных работ не блокирует публикацию.
6. Можно связать проект с конкретной ролью.
7. Один проект можно связать с несколькими ролями.
8. Назначение хранит отдельное описание вклада.
9. Несуществующий проект блокирует публикацию связи.
10. Draft-проект не раскрывается публичной связью.
11. Логотипы и cover проверяются и оптимизируются.
12. Все данные проходят JSON Schema.
13. Публикация записывает `career.json` последним.
14. Ошибка загрузки не повреждает публичную версию.
15. ETag защищает от потери внешних изменений.
16. Перед перезаписью создаётся backup.
17. Работает восстановление backup.
18. Секреты отсутствуют в browser bundle и логах.
19. API по умолчанию доступен только на localhost.
20. Предпросмотр соответствует публичным компонентам.
21. Можно импортировать и экспортировать JSON.
22. Есть diff перед публикацией.
23. Основные операции покрыты тестами.
24. Существующее управление проектами и профилем не ломается.
25. Изменение карьеры не требует deploy GitHub Pages.
26. Можно связать новую должность с предыдущей и указать тип перехода.
27. Переход отображается в timeline и preview.
28. Для каждой должности независимо редактируются обязанности, деятельность, результаты и ключевые факты.
29. Для компании показывается корректный общий срок без двойного подсчёта.
30. Можно сгенерировать или загрузить PDF и опубликовать кнопку скачивания.
31. Можно добавить, изменить и отключить ссылку hh.ru.
32. PDF и hh.ru управляются без deploy публичного сайта.
